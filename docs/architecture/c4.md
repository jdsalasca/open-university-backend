# Arquitectura C4

Diagramas objetivo de la plataforma final. Los adaptadores a legados son temporales y desaparecen por dominio después de cada corte aceptado. La identidad federada es un actor externo a confirmar con DTIC.

## Nivel 1 — Contexto

```mermaid
flowchart LR
  Comunidad[Estudiantes, docentes y personal UPTC]
  Operadores[Operadores académicos y administrativos]
  Administradores[Administradores institucionales autorizados]
  Plataforma[Plataforma universitaria UPTC\nSistema institucional unificado]
  IdP[Proveedor institucional de identidad\npor confirmar con DTIC]
  Legados[Portafolio de sistemas existentes\nfuente por dominio hasta su corte]
  Proveedores[Pagos, correo, firma y otros\nsolo tras inventario]

  Comunidad -->|consulta y tramita su vida universitaria| Plataforma
  Operadores -->|gestiona procesos autorizados| Plataforma
  Administradores -->|administra accesos e identidad visual| Plataforma
  Plataforma <-->|autenticación federada| IdP
  Plataforma <-->|integración/migración temporal por dominio| Legados
  Plataforma <-->|interfaces institucionales aprobadas| Proveedores
```

## Nivel 2 — Contenedores

```mermaid
flowchart LR
  Browser[Navegador]
  Frontend[Monolito frontend\nRepo Universiry-frontend\nVite + React + TypeScript + SCSS]
  Backend[Monolito backend modular\nRepo Universiry-backend\nJava 25 + Spring Boot + API REST]
  DB[(MySQL institucional\ntransacciones y migraciones Flyway)]
  DevDB[(MySQL 8.4 local\nvolumen aislado para desarrollo)]
  Assets[(Almacenamiento de activos\ninterfaz sustituible; filesystem local en desarrollo)]
  IdP[Identidad institucional\nOIDC/SSO por validar]
  Legacy[Adaptadores temporales a legados\nretirados al completar cada dominio]
  DevCompose[Docker Compose local\nsolo desarrollo; MySQL + Compose Watch]

  Browser --> Frontend
  Frontend -->|HTTPS, contrato OpenAPI| Backend
  Backend --> DB
  Backend --> Assets
  Backend <-->|tokens y claims autorizados| IdP
  Backend <-->|API/ETL de dominio| Legacy
  DevCompose -. orquesta localmente .-> Frontend
  DevCompose -. orquesta localmente .-> Backend
  DevCompose -. MySQL de desarrollo .-> DevDB
```

## Nivel 3 — Componentes del backend modular

```mermaid
flowchart TB
  Web[Adaptadores REST y validación de transporte]
  Security[Spring Security\nroles y autenticación federada]
  I18n[Catálogo de mensajes\nbase es-CO + bundle inglés]
  UseCases[Casos de uso\ncontratos de aplicación]
  Branding[Identidad visual\ntema, logos, módulos y banners]
  Identity[Identidad y autorización]
  Student[Persona, estudiante y ciclo]
  Academics[Programas, currículo, mallas, asignaturas y carga]
  Other[Bienestar, talento humano, finanzas, investigación y servicios\npor fases]
  Audit[Auditoría de cambios administrativos]
  Persistence[Adaptadores MySQL y Flyway]
  MediaValidation[Validador de imágenes\nfirma, decodificación y límites]
  AssetStorage[Puerto de archivos\nadaptador local en desarrollo]
  AssetRepository[Adaptador JDBC de medios\nmetadatos y publicación vigente]

  Web --> Security
  Web --> I18n
  Security --> I18n
  Security --> UseCases
  UseCases --> Branding
  UseCases --> Identity
  UseCases --> Student
  UseCases --> Academics
  UseCases --> Other
  Branding --> Audit
  Identity --> Audit
  Student --> Audit
  Branding --> Persistence
  Branding --> MediaValidation
  Branding --> AssetStorage
  Branding --> AssetRepository
  Student --> Persistence
  Academics --> Persistence
  Other --> Persistence
```

Los módulos comparten proceso y MySQL al inicio, pero no escriben las tablas de otros dominios sin pasar por contratos de aplicación. Las dependencias van desde adaptadores hacia casos de uso y dominio; Spring sirve para componer límites y persistencia, no para delegar reglas de negocio a controladores.
